# RFC: Native Module Structure and Build System

## Summary
This RFC outlines the standard directory structure, required files, and build system configuration (CMake) for developing C++ native modules for LodeRuntime. It also introduces the high-level Lode C++ API used for bridging C++ and Luau.

## Motivation
To ensure native plugins are portable, cross-platform, and easily consumable by Luau code, we need a standardized project layout. Developers must know exactly how to structure their source code, how to compile it so the runtime can find it, and what C++ APIs are available to interact with the Luau virtual machine.

## Design Details

### 1. Standard Directory Structure
A typical native module should follow this layout:

```text
my_native_module/
├── CMakeLists.txt         # Build configuration
├── lode.json              # Platform/Architecture library mapping
├── init.luau              # Type definitions for LSP and internal path anchor
├── src/
│   └── main.cpp           # C++ source code using Lode API
└── libs/                  # (Auto-generated by CMake)
    ├── windows/x64/Debug/
    ├── windows/x64/Release/
    ├── linux/arm64/
    └── macos/x64/
```

### 2. Required Files
- **`init.luau`**: Crucial for providing Luau type exports so the Language Server Protocol (LSP) can offer autocompletion to consumers. It also serves as the anchor directory for resolving `@self/` imports made within the C++ code.
- **`lode.json`**: The manifest file that tells the `LodeRuntime` exactly where to find the `.dll`, `.so`, or `.dylib` based on the user's OS and CPU architecture.

### 3. Build System (`CMakeLists.txt`)
We recommend using CMake to compile native modules. The build script should dynamically detect the target platform and architecture, and output the compiled shared library directly into the `libs/` folder in a structure that perfectly matches `lode.json`.

**Key CMake Behaviors:**
1. **Platform Detection:** Detects `WIN32`, `APPLE`, `ANDROID`, `EMSCRIPTEN`, or Linux variants to determine the folder name (e.g., `windows`, `macos`, `linux`) and file extension (`.dll`, `.dylib`, `.so`).
2. **Architecture Detection:** Detects `x64`, `x86`, `arm64`, or `wasm` based on the compiler's target processor.
3. **Dynamic Output:** Uses `POST_BUILD` custom commands to automatically copy the compiled binary into `${CMAKE_CURRENT_SOURCE_DIR}/libs/${TARGET_PLATFORM}/${TARGET_ARCH}/$<CONFIG>/`, keeping each build configuration's binary in its own subdirectory. The runtime resolves the `$<CONFIG>` subdirectory that matches its own build (see [RFC 01](01-module-resolution.md)), so Debug and Release builds never overwrite each other's shipped library.

This ensures that developers only need to run the build command, and the resulting library will instantly be placed where `lode.json` expects it.

### 3.1. Exporting the Build Configuration

Modules built through the Lode CMake define `LODE_BUILD_CONFIG_NAME` per configuration and export the `LodeModuleConfig` symbol (via `LODE_MODULE_CONFIG_EXPORT` in `include/Lode/Module.hpp`) so the runtime can verify that the module's CRT/STL ABI matches its own before calling `LodeModuleInit`. No config token is emitted when the definition is absent, letting third-party modules remain loadable as unverifiable.
